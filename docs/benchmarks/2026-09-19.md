## Method and environment

Measured on a GitHub Actions Ubuntu 24.04 VM, AMD EPYC 7763, four logical CPUs on two exposed physical cores (SMT enabled). Rust 1.98.1, Go 1.27.1, GCC 13.3. Rust was built with `cargo build --release --locked`; C with `-O3 -DNDEBUG`.

Proxy, origin and generator were pinned to logical CPUs 0, 1 and 2 respectively. **CPU 0 and CPU 1 are SMT siblings on the same physical core: this is not full physical-core isolation.** Both proxies had the same one-logical-CPU affinity. Rust used one Tokio worker; Go used GOMAXPROCS=1.

Each round had 1 second warmup and a 4-second measured admission window. Throughput includes draining requests admitted before the deadline. Latency covers complete successful response bodies. Tables show medians of three per-round measurements, not pooled percentiles. Configurations used MaxClients 1024; Rust additionally used MaxInflightRequests 1024 and MaxConcurrentStreams 32. Normal request logging, authentication and filter-list costs were not enabled in throughput tests; source ACLs allowed localhost only.

These are short **closed-loop, fixed-concurrency, loopback tests**, not WAN measurements, fixed-arrival-rate SLOs, long soak tests, or a comprehensive security audit. CPU/RSS sampling spans warmup and measurement; peak RSS is resident process memory, excluding kernel socket memory and virtual stack reservations. The raw data includes direct-to-origin controls and generator/origin CPU usage to expose test-side bottlenecks.

The concurrency-32 RPS ranges across rounds were 3,088.3–3,125.1 for C and 5,154.1–5,243.7 for Rust. Median proxy CPU utilization was 95.0% and 97.2% of their assigned logical CPU respectively; generator utilization was 55.9% and 78.4%. The generator was not at its own observed saturation point in these paired proxy cases, but shared-core contention remains a limitation.

When client reuse was allowed at concurrency 32, C achieved 3,183.1 req/s and Rust 6,519.2 req/s. **That 2.05x comparison includes a connection-behavior difference:** C redialed a median 15,962 times including warmup, whereas Rust used 32 TCP connections. It must not be described as an identical connection-lifecycle comparison. Rust still opens HTTP/1.1 origin connections per request; origin pooling is not implemented here.

## 2. HTTP/2: a real fixed-delay problem and a controlled experiment

1 KiB response. One client-to-proxy HTTP/2 connection for concurrency 1 or 32; TLS cases validate the localhost certificate and negotiate ALPN h2.

| Proxy hop / concurrency | Baseline req/s | NODELAY req/s | Baseline p50 ms | NODELAY p50 ms | Baseline p99 ms | NODELAY p99 ms |
|---|---:|---:|---:|---:|---:|---:|
| h2c / 1 | 24.4 | 3,249.9 | 41.004 | 0.300 | 41.093 | 0.399 |
| h2c / 32 | 751.1 | 6,495.8 | 42.959 | 5.013 | 43.523 | 6.597 |
| TLS h2 / 1 | 24.4 | 3,109.2 | 41.002 | 0.317 | 41.103 | 0.383 |
| TLS h2 / 32 | 754.6 | 6,305.5 | 42.655 | 5.171 | 44.073 | 6.773 |

The unchanged baseline therefore has an approximately 41 ms wait in these low-concurrency small-response workloads, despite passing functional tests. The separate NODELAY build removes that wait. At 32 concurrent TLS h2 streams, measured throughput increases **8.36x** and p99 falls from 44.073 to 6.773 ms. Baseline proxy CPU in that case was only 11.5%; the experimental binary reached 97.7%, consistent with removing an I/O wait rather than speeding up an already CPU-bound implementation.

The only runtime change in the experiment is `set_nodelay(true)` at the accepted socket and after dialing an outgoing socket. Tokio documents that this disables Nagle buffering: https://docs.rs/tokio/latest/tokio/net/struct.TcpStream.html#method.set_nodelay . The result supports a TCP buffering/delayed-ACK explanation, but no packet capture was taken to establish the detailed packet/ACK sequence. It is not evidence that HTTP/2 is inherently faster than HTTP/1. The experiment was not run at concurrency 128.

HTTP/2 here is the **client-to-proxy hop**. Plain HTTP origins are still reached over HTTP/1.1. HTTPS CONNECT remains an opaque tunnel. The benchmark does not measure an HTTP/2 origin pool or TLS interception.

## 3. Large transfers: gains, but NODELAY is not free

Concurrency 8, 1 MiB payload. MiB/s counts one payload direction. POST returns the uploaded payload; CONNECT echoes the payload back, so total two-way traffic is larger.

| Workload | C MiB/s | Rust baseline MiB/s | NODELAY MiB/s |
|---|---:|---:|---:|
| GET, fresh HTTP/1 | 341.9 | 1,030.9 | not measured |
| POST + response, fresh HTTP/1 | 265.2 | 391.2 | 351.4 |
| Established HTTP/1 CONNECT echo | 125.1 | 289.5 | 276.6 |

Rust's baseline GET throughput is 3.01x C in this workload, but no universal speed ratio follows from a short loopback test.

**The NODELAY experiment has a tradeoff:** POST throughput decreases 10.2%, although POST p99 improves from 57.390 to 25.751 ms. HTTP/1 CONNECT echo throughput decreases 4.5%; its proxy CPU utilization increases from 53.3% to 97.8%, while p99 improves from 49.235 to 35.255 ms. Those costs must be considered before broadly enabling the option. HTTP/2 small-response latency and bulk TCP relay buffering should be tuned separately.

Baseline HTTP/2-over-TLS CONNECT echo measured 307.5 MiB/s. It has different framing/encryption costs from plaintext C/H1 CONNECT and is not used as an equal-transport C comparison.

## 4. Held CONNECT tunnels: fewer threads and sockets, not lower RSS than C

The following are single short observations with 512 successfully established tunnels, not repeated load/soak tests:

| Implementation | Client TCP connections | Proxy RSS MiB | Threads | Proxy FDs | Idle CPU % |
|---|---:|---:|---:|---:|---:|
| C / HTTP/1 | 512 | 10.77 | 513 | 1,028 | 0.00 |
| Rust / HTTP/1 | 512 | 20.32 | 2 | 1,034 | 0.00 |
| Rust / TLS HTTP/2 | 16 | 17.82 | 2 | 538 | 0.33 |

C has lower resident memory in these cases. Rust reduces threads, and H2 multiplexing reduces client-facing TCP sockets. Each CONNECT tunnel still requires its own origin socket. Do not turn the thread count or virtual stack reservations into an unsupported claim that Rust has lower actual memory use.

One second after clients closed, descriptors returned to the before-load counts for every idle case: 4 for C and 10 for Rust. That observation is encouraging but not a proof of long-duration leak freedom.

## Recommended next measurements

Prioritize the demonstrated small-response wait, while preserving the measured bulk-transfer tradeoff. Test accepted/outgoing socket options separately, preserve vectored I/O through transport wrappers, and compare bounded relay buffer sizes before applying one policy to every transport. Then evaluate origin connection pooling with its own correctness and lifecycle tests. These are recommendations based on this run, not already measured improvements.

See [METHODOLOGY.md](METHODOLOGY.md) and `.github/workflows/benchmark-e2e.yml` for reproduction commands, workload definitions, resource accounting and limitations. Neither this report nor the benchmark branch changes main or makes a universal superiority claim.
